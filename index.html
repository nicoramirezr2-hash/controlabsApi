1. ¿Qué es un Middleware en tu día a día? (La Analogía del Guarda del SENA)

Primero entendemos la necesidad: revisar una petición antes de que llegue a la lógica que registra el préstamo.

La necesidad antes del código

El filtro de entrada en la portería

Imagina que el controlador es el instructor dentro del ambiente de clase: recibe una solicitud y ejecuta la acción del sistema. Si cada solicitud llegara sin revisar, podrían guardarse préstamos incompletos o la aplicación tendría que repetir controles en varios controladores.

El middleware es como el guarda que revisa antes de dejar pasar. Puede registrar quién llegó y a qué ruta, comprobar que estén los datos requeridos o detener una solicitud inválida. Si la revisión termina bien, llama a next() para continuar; si encuentra un problema, responde con un error y no deja avanzar esa petición.

Pregunta para el equipo: ¿Qué problemas aparecerían si ControlLabs guardara un préstamo sin verificar el aula, el número del equipo y quién lo recibe?

Antes de seguir, anoten una consecuencia para los datos y otra para la persona que usa el sistema.

Recorrido de una petición POST /api/v1/loans
  1. 1. Cliente: envía los datos del préstamo.
  2. 2. Logger: registra método, ruta y hora; luego llama a next().
  3. 3. Validador: comprueba los valores recibidos; si son inválidos responde 400, si no, llama a next().
  4. 4. Ruta, controlador y servicio: ejecutan la operación y guardan el préstamo.

El middleware no reemplaza al controlador: prepara, revisa o enruta la petición antes de que la lógica del módulo actúe.

2. Anatomía de tu Middleware y el Poder de next()

Una función middleware recibe la petición, la respuesta y la forma de continuar o transferir un error.

Los tres argumentos de un middleware estándar

  • req (Request): datos y metadatos de la petición.
  • res (Response): permite responder, por ejemplo con res.status(400).json(...).
  • next (NextFunction): pasa el control a la siguiente capa; next(error) deriva el flujo al manejador de errores.
Una petición debe terminar con una respuesta o continuar. Si el middleware no hace ninguna de las dos cosas, el cliente queda esperando. Si ya enviaste una respuesta de error, no llames también a next().
src/middlewares/logger.middleware.ts
import { Request, Response, NextFunction } from 'express';

export const requestLogger = (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  const timestamp = new Date().toISOString();
  console.log(`[${timestamp}] ${req.method} ${req.originalUrl}`);
  next();
};

3. Interfaces de TypeScript para describir el DTO y validar la petición

El contrato ayuda al equipo a programar con una forma compartida; el middleware comprueba los datos reales recibidos.

Dos responsabilidades distintas

Una interfaz TypeScript como ICreateLoanDTO describe la forma esperada y ayuda durante el desarrollo. Como los tipos se eliminan al compilar, la interfaz no verifica por sí misma el JSON que llega por HTTP. Por eso el middleware debe hacer comprobaciones en tiempo de ejecución antes de que el controlador use esos valores.

Definimos el DTO en un archivo compartido para que middleware, controlador y servicio usen el mismo contrato, sin copiar la declaración. La validación de valores sigue siendo responsabilidad del código que se ejecuta.

Para esta práctica validaremos campos requeridos y tipos básicos. La autenticación y los permisos por rol se dejan para cuando el proyecto integre OAuth; no se simulará que un rol enviado en el body es confiable.
src/dtos/loan.dto.ts
export interface ICreateLoanDTO {
  aula: string;
  numeroPC: number;
  nombreGuardaEntrega: string;
  instructorRecibe: string;
}
Uso: describir el valor tras validarlo
const body: unknown = req.body;

if (typeof body !== 'object' || body === null || Array.isArray(body)) {
    res.status(400).json({ success: false, error: 'El cuerpo debe ser un objeto.' });
    return;
}

const loan = body as Record<string, unknown>;
if (typeof loan.aula !== 'string' || loan.aula.trim() === '' ||
        typeof loan.numeroPC !== 'number' || !Number.isInteger(loan.numeroPC) ||
        typeof loan.nombreGuardaEntrega !== 'string' || loan.nombreGuardaEntrega.trim() === '' ||
        typeof loan.instructorRecibe !== 'string' || loan.instructorRecibe.trim() === '') {
  res.status(400).json({
    success: false,
    error: 'Datos del préstamo inválidos.'
  });
  return;
}

next();

La interfaz describe el contrato; estas comprobaciones son las que inspeccionan el JSON en ejecución. En la actividad se completará la validación de todos los campos.

4. ¿Qué se implementaría en ControlLabs para este módulo?

Traducimos la necesidad en piezas pequeñas y aclaramos qué se construye ahora y qué queda para después.

A. Auditoría y Logging (requestLogger)

Trazabilidad de Tráfico HTTP

Propósito: Registrar información básica de cada petición HTTP que entra al sistema.
Aplicación en ControlLabs: Cada vez que un guarda registra un préstamo o un instructor acepta un inventario, el middleware captura la marca de tiempo, el método HTTP (POST, GET, PUT), la ruta consultada y emite un registro institucional en consola con formato estricto:

[AUDIT SENA] [2026-06-01T14:32:00.000Z] POST /api/v1/loans
B. Autorización por Roles / RBAC (verifyRole)

Protección de Endpoints Críticos

Propósito: Restringir rutas críticas según el rol institucional del usuario.
Aplicación en ControlLabs:

  • El endpoint POST /api/v1/loans se reservará para usuarios autenticados con rol Guarda.
  • El endpoint PUT /api/v1/loans/:id/accept se reservará para usuarios autenticados con rol Instructor.
  • Sin autenticación corresponde 401 Unauthorized; con sesión válida pero rol insuficiente, 403 Forbidden. Se implementará cuando exista autenticación; el rol debe provenir de la identidad verificada, no de un valor arbitrario enviado por el cliente.
C. Validación de Payload (validateLoanPayload)

Contrato DTO Estricto

Propósito: Comprobar en tiempo de ejecución que los datos enviados en un POST tengan los campos y tipos básicos esperados antes de llegar al controlador.
Aplicación en ControlLabs: Comprueba que aula, numeroPC, nombreGuardaEntrega e instructorRecibe existan y tengan el tipo esperado. El DTO describe esa forma para TypeScript, pero no reemplaza esta comprobación.

D. Interceptor Global de Errores (errorHandler)

Manejo Centralizado de Excepciones

Propósito: Centralizar los errores que Express recibe o que una capa deriva explícitamente con next(err).
Aplicación en ControlLabs: Express busca el manejador de cuatro parámetros (err, req, res, next) y responde con un JSON estandarizado, sin exponer detalles internos al cliente:

{

  "status": "error",

  "message": "Error interno del servidor en ControlLabs",

  "timestamp": "..."

}

5. Orden Estricto de Registro en src/app.ts

En Express, el orden en el que declaras los middlewares es vital para que la cadena de ejecución funcione correctamente.

  1. Middlewares Globales Iniciales: cors(), express.json().
  2. Middleware de Auditoría y Logging: app.use(requestLogger) (registra todas las peticiones entrantes).
  3. Rutas de la API: app.use('/api/v1/loans', loanRoutes) (aquí operan middlewares específicos como validadores DTO).
  4. Respuesta 404 (Ruta No Encontrada): después de montar las rutas, una capa final responde cuando ninguna ruta coincide. Un 404 no es por sí solo un error lanzado a next(err).
  5. Manejador Global de Errores: app.use(globalErrorHandler) va después de rutas y demás middleware para recibir los errores derivados con next(err).
src/app.ts: orden de montaje
app.use(cors());
app.use(express.json());
app.use(requestLogger);

app.use('/api/v1/loans', loanRoutes);

app.use((_req, res) => {
  res.status(404).json({ success: false, error: 'Ruta no encontrada.' });
});

app.use(globalErrorHandler);

El parser JSON debe ir antes de las rutas para que req.body esté disponible. El manejador de errores se registra al final.

Auditoría automática de tráfico.

// 📁 src/middlewares/validateLoan.middleware.ts
import { Request, Response, NextFunction } from 'express';

export const validateLoanPayload = (
    req: Request,
    res: Response,
    next: NextFunction
): void => {
    const body: unknown = req.body;
    if (typeof body !== 'object' || body === null || Array.isArray(body)) {
        res.status(400).json({ success: false, error: 'Cuerpo inválido.' });
        return;
    }

    const loan = body as Record<string, unknown>;
    if (typeof loan.aula !== 'string' || loan.aula.trim() === '' ||
            typeof loan.numeroPC !== 'number' || !Number.isInteger(loan.numeroPC) ||
            typeof loan.nombreGuardaEntrega !== 'string' || loan.nombreGuardaEntrega.trim() === '' ||
            typeof loan.instructorRecibe !== 'string' || loan.instructorRecibe.trim() === '') {
        res.status(400).json({ success: false, error: 'Faltan datos válidos del préstamo.' });
        return;
    }
    next();
};

Validación estricta de contrato DTO.

// 📁 src/middlewares/errorHandler.middleware.ts
import { Request, Response, NextFunction } from 'express';

export const globalErrorHandler = (
    err: unknown,
    _req: Request,
    res: Response,
    _next: NextFunction
): void => {
    console.error(err);
    res.status(500).json({
        status: 'error',
        message: 'Error interno del servidor en ControlLabs'
    });
};

Regístralo al final de app.ts. En Express 4, deriva explícitamente los errores de operaciones asíncronas con next(error) o usa un wrapper; Express 5 también deriva los rechazos de promesas de handlers asíncronos.

7. Actividad guiada: construir y comprobar el pipeline

El propósito no es crear archivos por crear: cada paso responde a una necesidad concreta de ControlLabs.

Objetivo de la actividad

Al terminar, el equipo podrá enviar una petición de préstamo, observarla en el logger, rechazar datos incompletos con 400, dejar pasar datos válidos al controlador y devolver errores inesperados con una respuesta JSON consistente.

Pregunta guía: ¿Qué fallo evita cada archivo y cómo comprobará el equipo que funciona?

Paso 1

Crear la carpeta de middlewares

Crea el directorio src/middlewares/ dentro de tu proyecto backend.

Paso 2

Codificar el Logger de Auditoría

Crea logger.middleware.ts y prueba el registro de auditoría en tu consola al realizar peticiones GET.

Paso 3

Definir el DTO y el validador

Crea src/dtos/loan.dto.ts para compartir el contrato y validateLoan.middleware.ts para revisar valores reales en tiempo de ejecución.

Paso 4

Conectar el flujo en app.ts

Codifica errorHandler.middleware.ts con sus 4 parámetros y regístralo después de las rutas y del manejador 404.

Paso 5

Probar los resultados esperados

Con Thunder Client / Postman, comprueba: solicitud válida continúa; campo requerido ausente devuelve 400; ruta inexistente devuelve 404; error derivado con next(err) devuelve 500 sin stack trace público.

Ejercicio de prueba: observar el POST de un préstamo

En Thunder Client o Postman crea una petición POST http://localhost:3000/api/v1/loans, selecciona Body → JSON y envía cada objeto por separado. Ajusta el puerto si tu servidor usa otro.

Prueba A · Datos válidos

{
  "aula": "301",
  "numeroPC": 12,
  "nombreGuardaEntrega": "Laura Gómez",
  "instructorRecibe": "Carlos Ruiz"
}

Esperado: logger registra el POST → validador llama a next() → controlador recibe el préstamo. La respuesta final depende del controlador; si crea el recurso, normalmente será 201.

Prueba B · Falta un campo requerido

{
  "aula": "301",
  "numeroPC": 12,
    "instructorRecibe": "Carlos Ruiz"
}

Falta nombreGuardaEntrega. Esperado: logger registra el POST → validador responde 400 → no se llama a next() ni se ejecuta el controlador.

Prueba C · Tipo de dato incorrecto

{
  "aula": "301",
  "numeroPC": "doce",
  "nombreGuardaEntrega": "Laura Gómez",
  "instructorRecibe": "Carlos Ruiz"
}

Esperado: logger registra el POST → validador detecta que numeroPC no es número y responde 400 antes del controlador.

Prueba D · Error del servidor

Envía GET http://localhost:3000/__test/error después de añadir temporalmente la ruta que aparece abajo.

Esperado: logger registra el GET → la ruta llama a next(error) → manejador global responde 500 con JSON genérico, sin stack trace.

Ruta temporal para provocar el 500 (solo desarrollo)

Agrégala en src/app.ts después del logger y antes del manejador 404 y del manejador global. Elimínala al terminar la prueba.

app.get('/__test/error', (_req, _res, next) => {
  next(new Error('Error de prueba'));
});

Respuesta esperada: { "status": "error", "message": "Error interno del servidor en ControlLabs" }

Qué observar y registrar en la bitácora

  • En consola debe aparecer una línea de auditoría por cada intento, incluso para los cuerpos inválidos, porque el logger corre antes del validador.
  • En las pruebas B y C, confirma que la respuesta sea 400 y que no se cree ningún préstamo; la prueba B verifica específicamente nombreGuardaEntrega.
  • En la prueba A, confirma que llega al controlador y observa el estado y JSON que este devuelve.
  • En la prueba D, confirma que el error llega al manejador global y que la respuesta no revela el mensaje interno de prueba ni el stack.
  • Explica por qué cambiar 12 por "12" cambia el resultado, aunque ambos parezcan representar el número doce.

💡 Nota Importante de Integración:

Construiremos las capas de registro, validación y manejo de errores. La autorización por roles queda para una sesión posterior, cuando exista autenticación real; escribir verifyRole ahora sin una identidad verificada daría una falsa sensación de seguridad.
